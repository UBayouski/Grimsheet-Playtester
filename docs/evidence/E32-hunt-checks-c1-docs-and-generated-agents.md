## Generated agent files (what the gateway made from the app's agent JSON)
`~\.kiro\agents\hunt-checks--checker-ask.json` and `~\.kiro\agents\hunt-checks--checker-open.json` hold the keys `name`, `description`, `tools`, `resources`, `prompt`, `mcpServers` (empty object). `tools` is `["execute_bash"]` in both. **`allowedTools` is `[]` in both**, including `checker-open`, whose source file in `agents/checker-open.json` says `"allowedTools": ["execute_bash"]`. So the gateway did not carry the app's `allowedTools` value into the agent file it uses.

## What the Crew documentation says (Context7, not observed)
1. `agent-spec-fields.md`, "Ownership and refresh": an APP agent is generated by the App Kit, which owns "the fields that are containment rather than preference": `tools`, `allowedTools`, `prompt`, `managedToolPolicy`, `includeMcpJson` and `resources`; they are regenerated on refresh. This matches the empty `allowedTools` above.
2. `agent-spec-fields.md`, "Tools and permissions": `allowedTools` is "what is AUTO-APPROVED", entries are globs; it is the one path that never reaches Crew's PreToolUse gate, so every writer filters it through the governance ceiling.
3. `app-kit-platform.md`, section 2: a granted MCP server normally lands in the agent's `allowedTools` (auto-approve), "for an unattended app agent a prompt resolves to 'rejected', so granting it means granting its use". This is about granted MCP servers, not about `execute_bash`. It also says that for an unattended app agent a prompt resolves to "rejected" (relevant to C2: a message cron has nobody to approve).
4. Narrowing `execute_bash` to given commands, documented forms:
   - `permissions.rules` in the agent JSON (kiro-cli custom agent configuration reference): `{"permissions":{"rules":[{"capability":"shell","match":["node *"],"effect":"allow"}]}}` with `effect` `allow` (proceeds silently), `ask` or `deny`, `match` = command prefix globs, and `exclude`; "deny overrides". It is documented for kiro-cli custom agents. Whether the App Kit keeps a `permissions` block in a generated app agent is not documented; the generated files above hold no `permissions` key, but the source files had none.
   - `toolsSettings.shell.allowedCommands` / `deniedCommands`: deprecated for shell rules in favour of `permissions.rules`. Crew's `agent-spec-fields.md` says that on KAS (the engine used here) allow lists such as `allowedCommands` "are not carried, so those calls keep prompting", while `deniedCommands` become `deny` rules.
   - Gateway-level: a hook-based auto-approve by program NAME (`auto_approve_tools` globs and a read-only allowlist) with a check that the program name still resolves to the program it names; and per-cron `--approval-mode auto` ("auto-approve all tools without prompting"; empty = default hook-based approval) in `kirocrew cron add`, plus `ctx.set_session_mode` (`trust` or `trust_reads`) for a script cron. Whether a manifest cron accepts an approval-mode field is not documented in the notes (h, d).
5. Not documented: any prompt option such as "allow for this session" for an agent chat approval.

# Agent run 2 (checker-open, `allowedTools: ["execute_bash"]` in the app's agent file): C1 result (2026-11-07)
Agent run 2 of at most 5. Started by the developer in chat with agent `checker-open`; the developer approved each prompt. Source for the counts: the gateway's session log for this one chat (agent `checker-open`); no other session was opened.

- **Approval prompts: 3** (approval ids 2 to 4; the session log has 25 events, 3 `approval/requested`, 3 `approval/decided` all `approved`, 3 `tool/called`, 3 `tool/completed`). Prompted: the skill load (`disclose_context`, reason "Load skill: probe-skill"), the `node` command, and `Get-Date`. All three prompted, so **`allowedTools: ["execute_bash"]` removed no prompt**: not for a `node` command, not for a non-`node` command, not for the skill load.
- **Cause (documented, and visible in E32's first part):** the gateway generated `allowedTools: []` for this agent (the App Kit owns `allowedTools` of an app agent and regenerates it). **C1 result: `allowedTools` set in an app agent file is stripped and has no effect on approvals.**
- Allow-at-once option on any prompt (13.4): none noticed (developer's report; the log has no field for it).
- Approval record texts (the full command is in the record):
  - id 3: `node "~\.kiro\crew\apps\hunt-checks\skills\probe-skill/scripts/argv.mjs" hello; "exit code: $LASTEXITCODE"` (backslashes up to `probe-skill`, then `/scripts/argv.mjs`, as logged).
  - id 4: `Get-Date`.
  Note: the agent composed this `node` command itself and added a `;` chain with `$LASTEXITCODE` to the command, which the chat message did not ask for and which the shell rules forbid. The approval prompt is the only place where such an addition is visible. The raw script log shows `argv.mjs` received exactly one argument, `hello`.
- Outputs (as reported by the developer): `argv.mjs` printed `["hello"]`, exit 0; `Get-Date` printed the date, exit 0. The chat labelled the tool calls "Load skill: probe-skill", "Run argv probe script" and "Print current date" (a description, not the raw command as in run 1).

Run 1 cost 7.86 credits for 8 tool calls plus one failed 1000-character tool call. The gap supports (does not prove) the hypothesis that the failed long generation caused most of run 1's cost; run 2 also had fewer tool calls (3 against 8) and a shorter history.
