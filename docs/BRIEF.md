## 1. One-liner

Grimsheet Playtester is a Kiro Crew app that replays every Grimsheet level each night and sends an agent to break them.

Tagline: **The night watch for a haunted spreadsheet.**
Hackathon: Kiroween 2026, Best Kiro Crew App bonus, attached to the Grimsheet entry (category Frankenstein).
Deadline Dec 4, 2026, 2:00 PM PT. Feature freeze Nov 28.

## 2. Who it is for and why it matters

- The developer of a puzzle game, who needs to know two things after every change: do all levels still have their
  intended solution, and has a level become easier than intended.
- Grimsheet is the real case. Its five levels each have a stored solution with a `minimalInk` (the fewest formula
  edits needed). A change to the engine or a level file can quietly break a solution, or open a cheaper route that
  makes a level trivial. Unit tests check the solutions; nobody checks for new cheap routes.

The pitch for judges: an agent proposes exploits, and a deterministic engine checks every claim before it is
recorded. No finding reaches the dashboard unless replaying its action list reproduces it. That keeps the agent's
creativity and removes its guesswork.

## 3. What Grimsheet provides (the target)

- Public repo https://github.com/UBayouski/Grimsheet, branch `main`. Node 22+.
- `npm ci`, then `npm run build:play` writes `dist-play/headless.js`.
- `node scripts/play.mjs --list` lists level ids; `<level-id> --level-info` describes a level (map, cells with `raw`
  and `locked`, ink, HP, monsters).
- `node scripts/play.mjs <level-id> --actions-file <path>` plays an action list and prints JSON: `start`, one entry
  per step (`accepted`, `damage`, `hero`, `hp`, `ink`, `turn`, `status`), and `final`. Won means
  `final.status === "won"`; ink spent is `start.ink - final.ink`. Exit 2 means bad input.
- Actions: `{"kind":"move","dir":"N|S|E|W"}`, `{"kind":"wait"}`, `{"kind":"edit","address":"B14","raw":"7"}`.
- `tests/solutions/<level-id>.json` holds `levelId`, `minimalInk` and `actions` for each level.
- On Windows PowerShell, inline JSON arguments lose their quotes: always use `--actions-file`.

The Playtester never changes Grimsheet. It reads a fresh checkout and runs its command.

## 4. Two jobs

**Replay (nightly, no model call).** A cron `command` runs `node scripts/replay.mjs`:
1. Fetch Grimsheet `main` into the app data directory (shallow clone the first time, fetch and reset after), record
   the commit hash.
2. `npm ci` and `npm run build:play` in that checkout.
3. Play every stored solution. For each level record: won, end HP, ink spent, `minimalInk`, and the first step where
   the status changed.
4. Write one result file per run and update a bounded index (the last 30 runs).

A level is **green** when its solution still wins with ink spent equal to `minimalInk`, **red** when it no longer
wins, and **amber** when it wins with a different ink count.

**Hunt (weekly and on request, agent run).** The `playtester` agent, with the `find-exploits` skill, studies each
level (`--level-info`) and tries to find:
- a **cheaper win**: won with ink spent below `minimalInk`;
- a **free win**: won with zero edits on a level whose `minimalInk` is above 0;
- an **unexpected route**: a win that edits a cell the stored solution never touches.

Every candidate is written as an action list and replayed through `play.mjs` by the verifier. Only verified
candidates are recorded as findings, each with the level, the class, the commit hash, the action list and the replay
result. Rejected candidates are counted, not shown. The agent's attempt budget per level is fixed in the skill so a
run stays bounded.

## 5. Crew app parts

- `app.json`: `displayName`, semver `version`, `agents`, `skills`, `crons` (with `permissions.cron: true`), `ui`.
  Exact field use follows `docs/CREW_NOTES.md` section a.
- Agent `agents/playtester.json`: reads levels, writes candidate action lists, never edits Grimsheet files. Tied to its
  skills through `skill://` resources.
- Skills: `skills/play-level` (how to build and run the command and read the result; adapted from the
  `grimsheet-playtest` Kiro power's `play-level` skill in the Grimsheet repo, rewritten for a checkout in the app
  data directory) and `skills/find-exploits` (the three classes, the attempt budget, the candidate file format).
- Crons: `replay` nightly (`cron_expr`, a fixed timezone, `strict_schedule`), `hunt` weekly. Both can also be run by
  hand.
- Config: the Grimsheet repo URL and branch, defaulting to the values in section 3.
- `ui/` dashboard (React and Vite as the Crew docs require; the host provides `@kirocrew/app-sdk`, React and
  lucide-react, so they are build externals): one card per level with its colour, last result and trend over the
  last runs; a findings list with a copyable action list and the command that replays it; the commit hash and time of
  the last replay and hunt.

## 6. Open questions (answer first)

From `docs/CREW_NOTES.md`, not documented:
- How the UI reads files that a cron or agent wrote. This decides the result storage format. Answer it with a small
  spike before any other spec: the bundled `kirocrew-app-dev` skill, the `/websites/deepwiki_kirodotdev_kirocrew`

- Whether an agent or cron run can reach the network and clone a public repo, and whether Node is on its path on
  Windows. The spike checks both on this machine.
- How a skill listed in `app.json` maps into the agent's `skill://` glob.
If the spike shows the UI cannot read run output, the fallback is for the replay script to write its results where
the documented API can serve them, and the brief is updated before the specs are written.

## 7. Technical choices

- Node 22.12+ and git on the host; the README says so. Plain ESM JavaScript with JSDoc types and `// @ts-check` for
  the scripts, so a cron runs them with no build step. TypeScript strict for `ui/`.
- The verifier is a pure function from (level id, action list, `play.mjs` output) to a verdict, so it is unit-tested
  without Grimsheet.
- Tests: Vitest for the verifier, the result index and the replay script (with a fake play command); fast-check for
  the properties in section 10. No test depends on the network.
- No paid APIs, no hosting. The app runs in the user's own Kiro Crew. MIT licence.
- Written from scratch. It runs Grimsheet's command; it does not copy Grimsheet code.

## 8. Non-goals

- Writing to the Grimsheet repo in any way: no commits, branches, issues or pull requests.
- An exhaustive solver or proof that no cheaper win exists. The hunt is a bounded search; the README says so.
- Playtesting games other than Grimsheet, a hosted version, accounts, notifications outside Crew.
- Editing levels or suggesting fixes automatically.

## 10. Spec plan (in order)

1. `crew-spike`: a throwaway app proving the UI data path, network, Node on the path, and skill mapping. Findings go
   into `docs/CREW_NOTES.md`; the spike code is deleted.
2. `verifier`: action list and play output to verdict; the three exploit classes; green, amber, red.
3. `replay-runner`: fetch, build, replay all solutions, result files and bounded index, the `replay` cron.
4. `exploit-hunt`: the agent, the `find-exploits` skill, candidate files, verification, the `hunt` cron.
5. `dashboard`: the `ui/` pages over the stored results.
6. `packaging`: `app.json` final, install and trust steps for a judge (clone, build `ui/`, `kirocrew app install`,
   trust, enable), README.

## 11. Kiro plan (what to use and why)

- **Steering** (always): `product.md`, `tech.md`, `structure.md`. Conditional: `crew-app.md` on `app.json`,
  `agents/**`, `skills/**` (the documented manifest and agent rules from `docs/CREW_NOTES.md`), `dashboard.md` on
  `ui/**`.
- **Specs**: the six above, each with requirements, design and tasks.
- **Hooks**: run Vitest on save for `scripts/**` and `ui/src/**`; type-check and lint before the agent finishes a task.
- **PBT**: the verdict depends only on the play output (same output, same verdict); the result index never holds more
  than 30 runs and keeps the newest; a candidate is recorded only if replaying it reproduces its claimed class.
- **Powers**: Context7 for the Crew and app-sdk docs (already used for `docs/CREW_NOTES.md`). The `play-level` skill
  starts from the Grimsheet repo's `grimsheet-playtest` power.
- **MCP**: Playwright MCP to screenshot the dashboard for the README.
- **Surfaces**: the Kiro IDE and CLI to build it; Kiro Crew to run it. Record differences in `KIRO_USAGE.md`.
