## a. app.json manifest
Library `/kirodotdev/kirocrew`; pages `docs/app-kit/manifest-reference.md`, `skills/kirocrew-app-dev/SKILL.md`, `docs/app-kit/getting-started.md`.
- Required: `displayName` (gateway uses it for UI). `version` must be a semver string (used for `updateAvailable`). The docs' examples also always carry `name`, `description`, `author`. A formal required/optional table was not returned: "not documented" beyond this.
- Optional/other fields seen: `tags`, `iconPath`, `agents`, `skills`, `crons`, `permissions`, `ui`, `setup`, `sops`, `mcpServers`. Omit `resources`.
- Agents: `"agents": ["agents/sample-agent.json"]` (file paths).
- Skills: `"skills": ["skills/my-skill"]` (string paths to skill directories; legacy object entries are normalized).
- Crons: `crons` array (see d). A manifest with crons must also declare `"cron": true` in `permissions`.
- UI: `"ui": {"entry": "dist/index.mjs", "pages": [{"route": "/apps/<name>", "label": "...", "icon" or "iconUrl"}]}`, optional `sidebar`. `entry` is relative to `ui/`.
- `permissions` must be an object. Keys: `api`, `events`, `mcpTools`, `storage`, `network`, `memory`, `cron`, `sessionApproval`, `spawn`, `jobs`, `exposeToApps`. A non-object parses to empty.
- `setup`: `onInstall`, `onUninstall`, `onEnable`, `onDisable`.

## b. Agents
Library `/kirodotdev/kirocrew`; pages `docs/app-kit/getting-started.md`, `src/kiro_crew/docs/agents.md`, `docs/request-for-change/rfc-federated-app-platform.md`.
- Format: JSON file with `name`, `description`, `tools`, `allowedTools`, `resources`, `prompt`, `model`.
- Location in an app: any path listed in `app.json` `agents`; the examples use `agents/<name>.json` in the app root.
- Tie to skills: a `skill://<glob>` entry in the agent's `resources`, e.g. `"skill://.kiro/skills/*/SKILL.md"`. A custom agent with no `skill://` mapping gets no skill catalog (RFC page). How a skill declared in `app.json` is mapped into an app agent's `skill://` glob (the namespaced install path): not documented. → answered in section h.6 (observed 2026-11-07)

## c. Skills
Library `/kirodotdev/kirocrew`; pages `skills/README.md`, `src/kiro_crew/docs/skills.md`, `docs/reference/kiro-cli/skills.md`.
- Format: a folder with a required `SKILL.md` (YAML frontmatter plus Markdown body), optional `scripts/`, `references/`, `assets/`.
- Location in an app: `skills/<skill-name>/SKILL.md`, listed in `app.json` `skills`. Outside an app: `.kiro/skills/` or `~/.kiro/skills/`.
- Frontmatter fields: `name`, `description`, `always`, `triggers`, `inject_on_trigger`, `repo_scope`, `app`. None is required.

The play-level skill also has `license` and `metadata`; the docs do not list those, and whether they are accepted or ignored is not documented. → answered in section h.6 (observed 2026-11-07)
- Reuse as is? Not documented as safe. The file is a plain SKILL.md, so it would likely load, but its content assumes the Grimsheet repo root as the working directory (`npm run build:play`, `scripts/play.mjs`, `tests/solutions`). A run would need a Grimsheet checkout and Node. This is my reading of the skill file, not a Context7 statement.

## d. Crons
Library `/kirodotdev/kirocrew`; pages `docs/app-kit/manifest-reference.md`, `src/kiro_crew/docs/cron-and-scheduling.md`.
- Schedule: `every` (seconds) or `cron_expr` (5-field, e.g. `30 9 * * 1-5`), mutually exclusive. Optional `timezone` (IANA; default falls back to gateway zone, then UTC), `skip_dates` (`YYYY-MM-DD`), `strict_schedule` (otherwise a random start delay, up to 59 min on a daily job).
- Other fields: `name`, `message` (prompt sent to the agent), `agent`, `agent_sequence`, `command`, `script`, `env`, `persistent_session` (default true), `silent` (default false), `timeout`, `timeout_secs`, `enabled`, `folder`.
- What a run can do: an agent run with the `message` prompt; or a `command` (shell, no model call, default 300s timeout) or `script` (Python `file.py:function`, default 30s timeout).
- Output: delivered automatically unless `silent: true`. For Slack, to the conversation that scheduled the job. Where output goes for an app cron in the dashboard: not documented beyond the Schedule page listing the job. → answered in section h.7 (observed 2026-11-07)
- Not documented: pointing a cron at a specific git branch (e.g. Grimsheet's main). The agent would have to fetch it itself. → answered in section h.4 (observed 2026-11-07)

## e. Run environment
Library `/kirodotdev/kirocrew`; pages `src/kiro_crew/docs/apps.md`, `docs/guides/remote-crew-on-ec2.md`, `docs/guides/docker-troubleshooting.md`, `docs/request-for-change/rfc-app-sandbox-isolation.md`, `docs/app-kit/getting-started.md`.
- Shell: agent commands run as subprocesses; on Linux they run in a user-namespace sandbox, and if none is available command execution fails closed unless `agent.sandbox_allow_unsandboxed_exec` is set. Windows behavior: not documented. → answered in sections h.4 and h.5 (observed 2026-11-07)
- Node: not guaranteed in the agent environment. The official Docker image ships git, curl, ripgrep, unzip, Python, kiro-cli and no `node` or `npm`. For building a UI the prerequisite is Node.js 22.12+ (24 LTS recommended). → answered in sections h.4 and h.5 (observed 2026-11-07)
- Network: `permissions.network` exists, but per the sandbox RFC page `mcpTools`, `cron` and `network` are "stored and shown at install with no runtime gate". Actual agent network policy: not documented. → answered in sections h.4 and h.5 (observed 2026-11-07)
- Cloning a public GitHub repo from a run: not documented. `git` is present in the Docker image, and registry installs clone from any git-cloneable URL. → answered in sections h.4 and h.5 (observed 2026-11-07)
- Writing files: the SDK exposes an app-scoped data directory (`getAppDataDir()`). Other writable locations: not documented. → answered in sections h.3, h.4 and h.5 (observed 2026-11-07)
- App code itself runs in the gateway with the same privileges as Kiro Crew (no process sandbox); third-party apps are denied until trusted.

## f. ui/ and @kirocrew/app-sdk
Library `/kirodotdev/kirocrew`; pages `docs/app-kit/getting-started.md`, `docs/app-kit/migration-guide.md`, `docs/app-kit/api-reference.md`, `docs/system-specs/modules/app-kit-platform.md`, `docs/request-for-change/rfc-federated-app-platform.md`.
- Data: `useAppApi()` gives `get/post/put/delete` against gateway `/api/...` paths; `useAppEvents(event, cb)` subscribes to WebSocket events. Both are limited to paths and events declared in `permissions.api` and `permissions.events` (undeclared access throws). Storage: `permissions.storage` exists and the SDK has `getAppDataDir`, `getAppConfig`, `setAppConfig`. How a UI reads files an agent or cron wrote: not documented; the app-dev skill suggests keeping a bounded `_index.json` in the app data directory. → answered in section h.3 (observed 2026-11-07). Correction (observed): Crew 0.12.0 does not export `getAppDataDir`, `getAppConfig` or `setAppConfig`; the page reads a cron result through `GET /api/apps/<app>/config`.
- Build: standard React + Vite project in `ui/`; `npm run build` produces an ESM bundle (`.mjs`). Do not `npm install @kirocrew/app-sdk`: the host provides it, plus React, ReactDOM and lucide-react, via an import map, so mark them as build externals. An RFC page also lists a `kirocrewApp()` Vite plugin; the getting-started page does not use it, so treat it as unconfirmed.
- Serve: the dashboard dynamically `import()`s `/apps/<app>/ui/<entry>` as an ESM module (no iframe). HTML is not served; only `.mjs`/`.js` etc.
- Shared UI components: `@kirocrew/app-sdk/ui` (`Card`, `CardTitle`, `PageHeader`, `StatCard`).
- Current SDK version: not documented. It is not published to npm per the migration guide. → partly answered in section h.3 (observed 2026-11-07): the runtime exports `APP_SDK_LEVEL` 1; no version string was found.

### h.1 Install and trust
- Question: how does a local app get installed, trusted, enabled and updated on Windows, and what survives an update or an uninstall?
- Answer: `kirocrew app install <absolute path>` copies the app folder to `~\.kiro\crew\apps\<name>` (it copies `data\` and anything else in the folder, and drops every `.git` and `node_modules` folder at any depth). It exits 0 with a warning that executable resources (agents, skills, crons) are not registered until the app is trusted. Trust and enable are done in the dashboard (Settings, Security, Third-party apps); `kirocrew app enable` was not needed. A reinstall needs trust again. To push a change to an installed local app use the dashboard Details (or Library menu) **Sync** button: it kept trust, dev mode and `data\`. The CLI could not do it: `app install` again refuses ("already installed"), and `app update <name> --source <dir>` fails with "No running gateway answered" while the desktop gateway runs. `kirocrew app uninstall <name>` works from the CLI with the gateway running, and both it and the dashboard uninstall leave `<app dir>\data` behind. A Sync moves `data\` aside and back: it failed with `[WinError 5] Access is denied` on a git pack `.idx` file while a run held files under `data\`, and again while a leftover `~\.kiro\crew\apps\.<name>-data-tmp` folder from the first failure existed; each failure left that folder behind and removed the installed `app-crons.json`. It worked on every try with no run active and no leftover folder. The CLI is bundled with the desktop app and not on PATH (run it by full path); `kirocrew --version` is 0.12.0. `kirocrew app dev <name>` serves the UI with no-store and live reload; the desktop window kept a cached failed bundle until it was reloaded. Final removal (checked at the end of the spike): `kirocrew app uninstall crew-spike` (no `disable` first) exited 0 with "removed 1 cron job(s) from scheduler" and "uninstalled crew-spike", plus a warning that the conversation pointers are left in place while a gateway runs. Afterwards `kirocrew app info crew-spike` answered "App 'crew-spike' is not installed" and the app was gone from `app list`, the Schedule page and the sidebar; the generated agent file `~\.kiro\agents\<app>--<agent>.json` and the namespaced skill folder were removed too. `~\.kiro\crew\apps\crew-spike` was still there holding only `data\` (7,023 files; the app's own 61 files were removed), and so was the job's `~\.kiro\crew\cron-history\<job id>.jsonl`; both had to be deleted by hand. The delete needed `attrib -r` first for the read-only git pack files.
- Basis: Observed.

### h.3 UI data path
- Question: how does the page read a result that a cron or agent wrote?
- Answer: through the config route. `GET /api/apps/<app>/config` returns the contents of `<app dir>\data\config.json`, read at request time, when the app declares `"/api/apps/<app>/config"` in `permissions.api` (the match is exact; one entry covers GET and PUT). A cron script can write a key into that file with the other keys kept (read, add the key, write a temp file in `data\`, rename it), and the page then sees it after a Refresh, with no reload. A PUT to the same route **replaces the whole object**: a page PUT of `{"spikeCounter":19}` removed the cron's `spikeLastRun` key and an earlier seed key. So the page must never PUT that route. Fallback, tested: a `.mjs` module written under the installed `ui\` after install is served (200, `no-cache`) and can be `import()`ed (`.json` answered 404 and `.txt` 403), but a Sync deletes it, and an import without a `?t=` cache-buster stays stale until the page is reloaded. The SDK offers no data-folder call: `useAppInfo()` returns `{name, version, permissions, active}` with no path, and `getAppDataDir`, `getAppConfig` and `setAppConfig` are not exported (a page that imported them failed to link at all). `/api/crons` (declared) returns per-job run state (`last_run_ts`, `last_status`, `is_running`, `consecutive_failures`, `next_run_ts`, `enabled`, `user_paused`) but no run output; `GET /api/crons/<id>` answers 405. **No event marks a finished run**: `useAppEvents` never fired for a run ending, so a page needs a Refresh button or a timer. Nothing updates without an action; a Refresh updates the HTTP routes and a cache-busted import. The config route's size limit is not documented and was not tested.
- Basis: Observed.
- Evidence: E09, E10, E14, E24 (rounds 1 and 2, freshness, R3b), E26. Screenshot E14: the sidebar with "Crew Spike" selected and a table of probe rows R0 to R7 under the heading "Crew Spike: read routes".

### h.4 Cron: node, network, clone, build
- Question: can a cron run reach the network, clone a public repo, build it and find `node` on Windows?
- Answer: yes, with a Python **script** cron. A `command` cron is vetted and denied at registration on a Windows gateway ("No POSIX shell available to run this command cron ... Use a script cron or an LLM `message` cron on this platform, or run the gateway under POSIX"), so it never appears on the Schedule page, enabled or not. A script cron (`"script": "scripts/probe_cron.py:run"`) is registered, listed on Schedule with Run and Delete, and runs as a **child process** of the gateway under its bundled Python (its parent pid was the gateway pid); the dashboard stayed responsive during a wait-mode run (max 53 ms against a 60 ms baseline). Its working folder is the KiroCrew install folder (`C:\Program Files\KiroCrew`), not the app folder, so the script finds its files from `__file__`. `node`, `npm` and `git` are on its PATH (Node v24.18.0, npm 11.16.0, git 2.53.0.windows.2). The manifest `env` does not reach the script (no `SPIKE_*` name appeared), so settings come from a control file the script reads. No environment variable names the app data folder; `<app dir>\data` was used and worked. From the launcher's child `node`: HTTPS to github.com answered 200, `git ls-remote`, shallow clone, `git fetch --depth 1` plus `reset --hard` (556 ms on the second run), `npm ci` (142 packages, 5 to 9 s), `npm run build:play` (under 1 s, `dist-play/headless.js` written) and `node scripts/play.mjs --list` (five levels) all worked; commit `6372d9a`. `%LOCALAPPDATA%` is in the cron's and its child's environment. Limits: the script limit is `timeout` (seconds, default 30). `timeout_secs: 900` alone did not raise it (killed at 30 s); `timeout: 120` let a 58.5 s run finish; `timeout: 5` killed the launcher and its `node` child at 5 s, which left a probe report `running` until the next run marked it `cut-short`. `timeout_secs` is the wake budget and must be at least `timeout + 5` (a Sync with 900 and 900 was refused with "need >= 905, got 900", keeping the old values). A scheduled `every: 120` job fired on time, recorded as `trigger: scheduled` (a Run-button run is `manual`). To pause a job the manifest route (`enabled: false` plus Sync) works when the Sync works (E26); `POST /api/crons/<id>/enable {"enabled": false}` pauses it from the dashboard session. A paused job's Run button is disabled ("Resume to run"); `POST /api/crons/<id>/run` still started it. A job's manifest `env` change is not applied to an existing job until the app is disabled and enabled again (gateway warning). Do not keep the clone in the app folder: the install drops `.git` and `node_modules`, and a Sync moves `data\` so read-only git pack files there made it fail (h.1).
- Basis: Observed.
- Evidence: E02, E03, E04 (hand runs of the probe), E17, E18, E20, E21 (latency CSVs), E22, E23, E25, E26, E27. Screenshots: E22 is the Executions list (the job row itself, with ID, name `crew-spike/probe`, "script python", "every 24h", the script path, a Ready status, Run and Delete buttons, was read from the page text, E20); the E25 screenshot of the same row with status Paused, next run none, Run (greyed) and Delete is not kept (shows a local path).

#### h.10.2 C3: what reaches Node through the agent shell (Windows PowerShell 5.1)
- Question: which argument forms reach Node unchanged, and what is the smallest safe escape set for a candidate argument?
- Answer (received by Node, from the script's own log; `["--actions", ...]`):

  - An unquoted list with a fully percent-encoded edit value (C3-f, `N edit:B14=%3DIF%28DIST%28HERO%2CSELF%29%3C1%2CTOWARD%28HERO%29%2C%22-%22%29 E`): arrives as `"N"`, the 74-character encoded value (one argument, intact), `"E"`.

The shell's handling of a 1000-character argument and the way an approval prompt shows a long argument were not observed. No spare run was spent. In practice a candidate argument is bounded by what the agent can write in one tool call: the longest one written and received was 74 characters.

## i. Packaging: how an API request carries the token
Checked on 2026-11-08 for the `packaging` spec (task 1.2), on Windows 11, Crew 0.12.0. Read only: the help text of `kirocrew token --help` and Kiro's documentation power for the library `/kirodotdev/kirocrew`. No token was printed, read or stored, and `kirocrew token` itself was not run.

- Question: which form does a request to the gateway's `/api/...` routes use for the dashboard access token, a header or a query parameter?
- Answer from the help text: `kirocrew token` prints "a dashboard access URL with auth token" and takes `--port`, `--ttl` (default 20h) and `--embed-parent-port`. The help text does not say how an API request carries the token.
- Answer from the documentation: the dashboard address built for a user has the form `http://<host>:<port>/?token=<token>` (module page `dashboard-token-auth`). The command `kirocrew pod api` makes one authenticated request to a pod's dashboard and "sends it via ?token= query parameter, never an Authorization header" (page `src/kiro_crew/pod/README.md`); that command refuses on Windows, so it is evidence of the form, not a way to run the request here. The header `Authorization: Bearer <token>` is documented for inbound webhooks, which is a different token and a different route family (page `inbound-webhooks`).
- Not documented: whether the app config route `/api/apps/<name>/config` and the route `/api/crons` accept the dashboard token in a query parameter on this gateway, whether they accept it in a header, and whether the dashboard sets a cookie after the first request. None of these was tried.
- Decision for the route reader of `packaging` (D6): the constant `TOKEN_FORM` is `query` by default (the form the documentation shows for the dashboard token) and `bearer` stays supported behind the same constant. ## l. The gateway token address is a login link
Packaging task 13, 2026-11-08, Crew 0.12.0. Evidence: E40. Cause not proven.

- Question: how long and how often can the address that `kirocrew token` prints be used by a program?
- Docs say (the Crew pages on dashboard token authentication and security): the `?token=` address is a login link with a 5-minute click window. On use it is exchanged for a session cookie named `mc_token_<port>`, whose lifetime is the session lifetime (up to 20 hours). The pages also say that presenting the same link again inside the window is allowed, and that each presentation gives a fresh cookie bound to the presenting peer.
- Observed: the route reader sends the link as `?token=` on every request and keeps no cookie. Runs that reused an address which an earlier command had presented were refused (403 on `/api/crons` or on the Config_Route); the one run whose process presented a fresh address first made 12 requests, all answered 200. This fits "a login link works for the process that presents it first and is refused for a later one" better than "a link serves two requests". The first real run (200 on `/api/crons`, then 403 on the Config_Route within milliseconds) is not explained by either. A token with a changed last character gave 403 "Forbidden" on `/api/crons` and 403 "invalid signature" on the Config_Route.
- Practical rule: use one fresh `kirocrew token` for each command, and paste it straight away. A dry run followed by a real run needs two addresses, or no dry run (the real run reads both routes before it writes).
- Not built: the reader could exchange the link for the session cookie on its first request and send only the cookie afterwards, as the browser does. That is an option if a later step needs one address across several commands.
- Basis: Docs say (the two pages), and Observed (E40).
